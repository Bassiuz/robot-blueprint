## Default: one repo per product
```
<product>/
  app/               # Flutter (mobile + web build)
  functions/         # Firebase Functions, TypeScript
  server/            # optional Python service for lifebase
  site/              # optional static landing page
  firebase.json  .firebaserc  firestore.rules  firestore.indexes.json
  README.md  CLAUDE.md  decisions.md  engineering.md
```
[`examples/tally/`](https://github.com/Bassiuz/robot-blueprint/tree/main/examples/tally) is this layout. When there is only an app, the Flutter
project can sit at the root instead of in `app/`.

## Separate repos, and why
- **`<app>-web`**: build output only, force-pushed by `build-web.sh` /
  `publish-website.sh` for GitHub Pages. Never edited by hand.
- **Reusable Dart packages** get their own repo (jewelry, test_laser,
  build_laser) and are used as path or git dependencies.
- **Data shared across many projects** gets its own repo, used read-only by
  path, never re-downloaded per project.

## When it grows (the work pattern)
When several apps and function codebases share one data model, the work setup splits:
- a **contract repo**: the data model as YAML schemas, the Firestore rules
  generated from config, a changelog per week;
- a **generator CLI** that turns the YAML into TS models and mappers, committed
  into each consumer (generated code, regenerated by hand);
- **function monorepos** (yarn workspaces: `shared`, `data`, `models`,
  `features/*`, `infra/*`);
- a **scripts repo** for one-off data fixes in dated folders with a README each.

Worth copying early: dated script folders, and a README per feature with
Purpose, Entrypoints, Data, Events, Security, Failure/recovery.
